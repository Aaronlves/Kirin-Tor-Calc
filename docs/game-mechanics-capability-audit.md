# 游戏机制计算能力审查

审查日期：2026-09-01。结论只覆盖期望值、等效值、阈值和参数曲线，不覆盖战斗时间线、动作优先级执行、单位行为或随机战斗模拟。

## 结论

当前内核对既定范围是**有条件地足够**：只要一种机制能被写成有限的标量公式，或作者已经把状态过程化简为触发率、覆盖率、期望次数等效参数，Kirin source 就能定义、校验、计算、比较、扫描和重放它。它不是通用的战斗算法语言；需要逐事件状态转移、动态目标集合或相关随机过程才能得到期望值的机制，当前不能直接定义，只能先在外部推导出等效公式。

这一区分很重要：“某个公式能算”不等于“工具能从技能说明自动推导完整循环”。

## 用来检查的现有游戏机制

暴雪对 Midnight 的设计说明仍把资源、关键增益与减益、技能充能和触发效果列为职业玩法的核心状态；这说明仅有一次伤害公式并不足以覆盖玩家计算需求。[官方设计说明](https://worldofwarcraft.blizzard.com/en-us/news/24235745/developer-insight-combat-for-everyone-in-midnight)

当前官方更新提供了适合本次审查的代表性机制形状：

- 按层数改变施法时间、消耗层数并按层增强效果；
- 固定概率触发、失败后概率变化、额外充能和冷却缩减；
- 生命值阈值、叠层上限、独立持续时间和周期伤害；
- 超过若干目标后伤害递减；
- 群体控制递减需要记住同类效果次数和 16 秒重置状态。

这些形状可见于 [Midnight 前夕更新说明](https://worldofwarcraft.blizzard.com/en-us/news/24244455/midnight-pre-expansion-content-update-notes) 和 [12.0.5 更新说明](https://worldofwarcraft.blizzard.com/en-us/news/24271855/1205-content-update-notes)。后续 [Curse of Ula'tek 更新说明](https://worldofwarcraft.blizzard.com/en-us/news/24293281/curse-of-ulatek-content-update-notes) 也继续把冷却、持续时间与玩家资源作为当前界面和玩法信息。官方说明通常只公开规则描述而不公开完整服务器公式；因此这里审查的是**已知公式的表达能力**，不把未公开系数猜成事实。

## 已由自动化测试证明的能力

`tests/test_game_mechanics_capabilities.py` 用测试自身声明的虚构游戏语义和数值构建游戏中立工作区，加载并校验 Kirin source，然后执行精确求值和扫描。核心不提供 WoW 数据；该测试也不是对游戏数值的断言，只证明下列公式形状可以运行：

| 机制形状 | Kirin 写法 | 能力结论 |
| --- | --- | --- |
| 暴击期望 | `base * (1 + crit * (crit_multiplier - 1))` | 原生支持精确概率和有理数 |
| 斩杀/生命阈值 | `if_else` / `piecewise` | 原生支持 |
| 目标软上限 | `piecewise`、`sqrt`、目标数输入 | 原生支持总量曲线 |
| 周期效果与急速 | `floor(duration / interval)` | 可算固定持续时间的等效跳数 |
| 充能等效秒伤 | `damage * charges / cooldown` | 可算稳态等效值 |
| 独立触发期望 | `proc_damage * chance * attempts_per_time` | 原生支持线性期望 |
| 护甲型有理减伤 | `damage * constant / (armor + constant)` | 原生支持并检查单位 |
| 层数封顶 | `min(stacks, cap)` | 原生支持 |
| 固定次数递减或连续失败 | 常数边界 `sum` / `product` | 原生支持有限离散期望展开 |
| 等级/装等换算表 | `lookup` / `interpolate` | 支持版本化精确查表与范围内线性插值 |
| 配装/天赋方案 | entry 内 `presets`、临时参数、最多 8 个方案 | 浏览器工作台可比较数值和曲线 |
| 单属性断点 | 单变量 `solve` | 浏览器工作台可按基准方案反求 |
| 多属性收支平衡 | `solve-system` | 最多 8 个有限符号方程/变量并检查输入范围 |
| 双属性收益面 | `grid` | 最多 10,000 个组合，浏览器热力图和 CSV |
| 秒/毫秒等同量纲单位 | 精确 unit scale | 输入、范围、查表、求解和结果统一换算 |

现有内核还支持布尔条件、跨文档函数与依赖、显式输入范围、整数和有限枚举、量纲及比例单位检查、精确/近似结果、单变量求导、单变量求解、有限联立方程，以及最多 10,000 点的一维或二维扫描。

## 能表达，但需要作者先给出等效模型

下列机制在不做模拟的前提下仍可计算，但“等效参数如何得到”不由当前内核负责：

- 冷却窗口、资源循环和动作优先级：把期望施放次数、资源净收入或覆盖率作为输入，或手写已经推导出的闭式公式；
- DoT 刷新、快照和动态更新：固定规则下可写总跳数与等效倍率，但时间轴上的刷新选择必须先化简；
- 伤害累积后爆发：可用“窗口内期望伤害 × 累积比例”，但工具不会自己运行窗口内循环；
- 多次触发、叠层或失败保护：固定次数可显式展开；稳态结果需要作者先解出等效触发率或有限状态模型；
- 群体控制递减：给定应用次数和是否超过重置时间后可用 `piecewise` 计算等效时长，但不会保存每个目标的递减状态；
- 不同天赋、装备、目标数和战斗阶段：可由条目内参数方案与输入离散比较，但工具不会搜索最佳动作序列。

这类结果应在 source 的说明和来源中标明“外部推导的等效参数”，避免把推导假设误当成游戏原始数据。

## 目前不能直接定义的算法

| 缺口 | 直接影响 |
| --- | --- |
| 没有状态机、递归或允许依赖环 | 不能逐事件描述资源、增益、充能、失败保护和重置过程 |
| 没有概率分布、条件期望或相关随机变量 | 不能自动组合相依触发；只能写加权和或闭式期望 |
| `sum` 只接受常数整数边界 | 不能按动态目标数或动态持续时间直接循环 |
| 没有列表、向量、矩阵和目标集合 | 不能分别保存多个目标的生命、减益或快照状态 |
| 联立求解只接受有限符号解，没有连续/离散优化器 | 可解已定义的多属性平衡，但不会自动寻找完整配装空间的全局最优点 |
| 没有对数、积分等更广泛数学语言 | 少数闭式稳态模型仍需作者先在外部推导 |
| 舍入只在公式显式使用 `floor`/`ceil` 时发生 | 服务器在多个中间阶段的取整规则必须逐处建模 |
| `wow` 初始化包只有通用量纲和值域 | 没有自动同步当前技能、天赋、等级系数、热修和版本数据 |

这些限制大多是明确的产品边界，而不是计算错误。版本化查表/插值、来源与游戏版本约束、有限离散期望、比例单位、二维收益面和有限联立求解已经补齐。若未来仍坚持“不模拟”，下一项真正有价值的扩展是小型有限状态稳态求解，而不是战斗事件循环。

## 玩家需求判断

对于“比较两套配装”“某属性增加多少伤害”“多少属性达到目标值”“目标数变化时总量如何”“某触发按给定触发率值多少秒伤”“某冷却按给定覆盖率值多少”等常见理论计算，当前工具已经够用。

对于“按当前优先级整场战斗实际能放几次”“带失败保护的触发在复杂循环中的真实分布”“多个目标各自刷新 DoT 的最优策略”等问题，当前工具不应声称能够直接回答。它只能接收这些问题经过外部分析后得到的期望次数、覆盖率或闭式模型。
